# S2: hide and unhide from an app that is not active

Spike of spec §16.1 (and §9.8), run 2026-09-29 on macOS 27.0, Apple
silicon, with profiles A and B. Harness:
[`spikes/Sources/SpikeRunner/`](../../spikes/Sources/SpikeRunner/), mode
`s2 --subject`.

**Verdict: pass.** 50 of 50 hides and 50 of 50 unhides worked from the
un-granted subject while another instance was active, which is the moment
Solo hides the previous profile (§9.2).

## Method

Each trial put one instance in front and made sure SpikeSubject, which holds
no Accessibility grant, was not active. The subject then called `hide()` on
the other, visible instance, then `unhide()`. Success means the workspace
notification arrived and `isHidden` agreed. Targets alternated A and B.

## Results

| Trials | Setup held | Hide and unhide both worked | Hide p50 / p95 | Unhide p50 / p95 | Front app changed |
|---|---|---|---|---|---|
| 50 | 50 | 50/50 | 3 / 7 ms | 2 / 6 ms | 0 of 100 calls |

- `hide()` and `unhide()` returned **false in all 100 calls**, although
  every one of them worked. Apple's header promises only that the request
  was sent (§9.8). The return value is not evidence either way; the
  notification is.
- Unhiding never activated the instance, and hiding never moved activation.

## Design consequences

- Solo is mechanically sound from Mode A: hiding needs no grant and no
  activation. Whether a hidden instance keeps working is S14's question,
  still open, and it decides D-06.
- §9.8: confirm a hide or unhide by its notification and `isHidden`, never
  by the call's return value.
