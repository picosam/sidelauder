# S14: do hidden or covered instances keep working?

Spike of spec §16.1 (and D-06, the default policy), run 2026-09-29 on
macOS 27.0, Apple silicon, with profile A answering and profile B's window
used only as a cover. Harness: `SpikeRunner s14` in
[`spikes/Sources/SpikeRunner/Hidden.swift`](../../spikes/Sources/SpikeRunner/Hidden.swift);
tables from [`spikes/summarize.py`](../../spikes/summarize.py).

**Verdict: pass for chat; Code not measured.** A chat answer finished no
later hidden or fully covered than in front, and was complete when A was
brought back at 1.1 × the visible time. The Code-tab task could not run: the
session asked for approval before every Bash call, even after "Always
allow", so no unattended run was possible. That is itself a finding (below).
Hiding for longer than 5 minutes, where Chromium throttles hardest, is
untested.

## How the runs were made

The operator sent the prompt in A and pressed ⌃⌥⇧1; the harness then applied
the condition:

- **visible**: nothing; A stays in front;
- **hidden**: `hide()` on A, confirmed by `isHidden`;
- **covered**: B's window set to A's frame plus 8 pt on each side and brought
  forward; the window list confirmed every window of A was inside B's and
  behind it, since Chromium counts a window as occluded only when nothing of
  it shows.

At 1.1 × the visible time T the harness put B back, unhid A and brought it
forward by step 1 (§9.7). The operator pressed ⌃⌥⇧2 if the answer was
complete, or ⌃⌥⇧3 and then ⌃⌥⇧2 when it finished. The harness sampled the
CPU of A's whole process tree (main process, renderers and helpers) every
250 ms and kept sampling after the finish mark until A was idle.

Chat prompt: "Write the numbers from 1 to 400 as English words, one per line,
with no other text."

**The end of the work is read from the CPU trace, not the hand mark.** Idle,
A sits at 1–4 %; streaming, it sits well above. A run's work ended at the
start of the first 3-second stretch whose median CPU is under 5 %. The finish
mark is kept as a cross-check: in the counted runs it came 1 to 8 s after
that point, which is the operator seeing the last line and reaching the keys.

## Results

| Condition | Applied | A back at | Complete at the reveal | Finish mark | Work ended (CPU) | CPU while working, median |
|---|---|---|---|---|---|---|
| visible | – | – | – | 15.4 s | 14.1 s | 64 % |
| hidden | hide held | 17.2 s, in front | yes | 18.6 s | 12.3 s | 10 % |
| covered | fully covered | 17.3 s, in front | yes | 21.7 s | 13.4 s | 63 % |

T was taken from the visible finish mark (15.4 s), so the reveal came at
17 s. Pass is "same completion within 10 %". Hidden and covered finished
earlier than visible, not later, so neither shows a slowdown. The 13 %
difference for hidden is ordinary variation between answers: each condition
ran once, and the model's own generation time varies from answer to answer.

**Hiding cuts A's CPU by about six times; covering saves nothing.** Hidden,
A streamed the same answer at a median 10 % CPU against 64 % in front. After
the reveal it was briefly busy (under a second at up to 165 %) and then idle,
so the text had arrived while hidden and only the painting waited. Fully
covered, A kept painting at its visible cost (63 %).

## Runs not counted

Three earlier chat runs were discarded because their hand marks did not
match what the operator saw: a start mark pressed twice, and two finish
marks pressed while the answer was still arriving (in one, at about line 90
of 400). They led to the CPU-based end above and to sampling every 250 ms,
so a reveal at a few seconds lands on time.

## The Code-tab task

The task was 15 separate Bash calls, each appending a timestamp to a file
and sleeping 4 s, so the gaps between timestamps would show any slowdown.
Three attempts in A's Code tab:

1. The session asked what the task was for instead of running it.
2. With the purpose stated, it ran, but asked for approval before every
   call; the operator's clicks made the gaps 4 to 7 s, which times the
   clicks, not A.
3. It asked again after "Always allow", and the operator stopped the run.

No hidden or covered Code run was possible: a hidden instance waiting for an
approval simply waits, because nobody sees the prompt. This does not show
throttling; it shows that a hidden Code session can stall for a reason
Sidelauder cannot see.

## What the runs cannot show

- **Hiding for longer than 5 minutes.** Chromium's strongest throttling of
  hidden pages starts after about 5 minutes; these runs hid A for 17 s. The
  operator kept the briefed length. Streaming text is driven by the network,
  not by timers, which is why it is not expected to throttle, but that is a
  reason, not a measurement.
- **Code sessions.** Their agent loop runs outside the renderer and was not
  measured at all.
- **Variation.** One run per condition; a difference under about 15 % is not
  resolved.

## Design consequences

- **D-06 decided: Solo.** Nothing measured shows a hidden or covered instance
  losing time, and hiding is the only condition that saves energy. Stack
  leaves the other windows covered, which costs as much as leaving them in
  front.
- **M1a checks the rest in daily use:** a long hidden answer (over 5 minutes)
  and a Code session hidden while it works, in a permission mode that runs
  without asking. If either stalls, Solo gains a "busy, don't hide" rule
  (R17).
- **A hidden instance can wait for an approval nobody sees.** Sidelauder
  acts on Claude's windows only, never inside them (I6), so it cannot tell. Whether Claude posts a
  notification for an approval request while hidden is unknown; M1a's daily
  use checks it. Until then this is a documented limit of Solo.
