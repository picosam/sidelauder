# S16: the interim adapter and finding upstream

Spike of spec §16.1, run 2026-09-29 on macOS 27.0, Apple silicon,
claude-multiprofile 0.1.31, Node 26.10. The tools are
in [`spikes/s16/`](../../spikes/s16/) and
[`spikes/Sources/Discovery/`](../../spikes/Sources/Discovery/); the adapter is
[`App/Sidelauder/upstream-status.mjs`](../../App/Sidelauder/upstream-status.mjs).
Profiles are called A and B here.

**Verdict: pass, with two changes to the spec.** The adapter agrees with
upstream on every state that could be shown, a call costs 124 ms (median) on
the event path, and an app started the way the Dock starts it found both
`claude-multiprofile` and `node` in 20 of 20 launches. The changes: the
adapter's slow facts move behind a flag, and discovery gets a second probe and
a hard kill.

## 1. Does the adapter agree with upstream?

| Compared against | What was compared | Result |
|---|---|---|
| `claude-multiprofile list` | Profile set, launcher paths, data folders, default app | Same, for every registered profile |
| `claude-multiprofile doctor` (read-only, run without npm on PATH) | Strays ("running without --user-data-dir"), shared accounts ("SAME account") | Same: none of either |
| The live process table | Default instance, and A and B launched through their launchers | All three `onProfile`, the same PIDs `ps` shows |
| Upstream's own functions, with a fixture home folder | `onProfile` (paths with spaces, an apostrophe, accents), `stray` (no data folder; an unregistered one), `foreignDataDir`, `sharedApp` (a profile without its own copy; a profile's folder on the default app), an unregistered folder on the default app, a stale copy, two profiles on one account, a Code-only profile, a corrupt registry | Every case as specified, 7 tests ([`Tests/Adapter/upstream.test.mjs`](../../Tests/Adapter/upstream.test.mjs)) |

`stray`, `foreignDataDir`, `sharedApp`, a stale copy and a shared account were
not produced live: each would mean starting a profile's copy outside its
launcher, rebuilding a copy, or signing a profile into another account. They
run through upstream's real functions against fixtures instead. Hidden state
is not an upstream fact (the process table is the same whether a window is
hidden or not), so "hidden" needs no comparison.

Four composition rules upstream does not export are named in the adapter's
header (E1 to E4). One was not foreseen by the spec: upstream's
`runningCopies` matches an app path anywhere in a command line, so
`/Applications/Claude.app` also matches `~/Applications/Claude.app`. The
adapter now claims each process once, longest app path first; a process of an
unregistered Claude whose path ends in a scanned one is still reported under
it, and the app's liveness check (§8.4) discards it on the bundle URL. The
unit, upstream and mutation gates (28 + 11 + 7 tests, 11 mutations each red)
hold the adapter to all of this.

## 2. What does a call cost?

Twenty calls each, spawned as the app will spawn them (empty environment,
`PATH` = node's folder plus `/usr/bin:/bin`), one Claude instance running:

| Call | First | Min | Median | p95 | Max |
|---|---|---|---|---|---|
| Default (instances and accounts) | 120 ms | 119 ms | **124 ms** | 128 ms | 130 ms |
| `--full` (adds launcher bundle IDs, helper use, copy staleness) | 280 ms | 271 ms | **281 ms** | 312 ms | 329 ms |

Where the time goes (medians of 10): starting Node 26 takes about 93 ms and
importing upstream's modules 11 ms; one `ps -axww` over about 1,000 processes
takes 48 to 54 ms; decompiling one launcher's script to see whether it uses
the helper takes about 50 ms, reading its bundle ID 3 ms, and comparing a
copy's version with its source 6 ms. The registry and account reads are under
1 ms.

Before the split, the one call cost 227 ms median, over the 200 ms target
(§12). The three facts that spawn a process per profile change only when a
launcher is rebuilt or Claude updates, so they moved behind `--full`: the app
asks for `--full` at start and when upstream's config folder changes, and for
the default answer on every Claude launch and exit.

A true cold call (empty file cache) was not measured: that needs `purge`,
which needs an administrator. The first call of each series above is the
coldest measured.

## 3. Can a Dock-launched app find upstream?

The Discovery app asks the user's login shell (`getpwuid`, not `$SHELL`) for
`command -v claude-multiprofile`, `command -v node` and `$XDG_CONFIG_HOME`
between marker lines, first with `-l`, then with `-l -i`, then runs the
adapter with what it found.

**A terminal is not the Dock.** On macOS 27 an app started with `open`, or
with `NSWorkspace.openApplication`, inherits the requesting process's
environment, PATH included. The first runs, started from a terminal, reported
the terminal's full PATH. The runs below were requested from a process
holding only the Dock's environment, and the app reported
`PATH=/usr/bin:/bin:/usr/sbin:/sbin`, as a Dock launch does.

| Shell setup | `-l` found both | `-l -i` found both | Time (`-l` / `-l -i`) |
|---|---|---|---|
| The test Mac's own, 20 launches | 20/20 | 20/20 | median 95 / 131 ms, max 108 / 137 ms |
| Fixture: the tools on no login-shell path | no | no | 70 / 72 ms |
| Fixture: tools set up only in `.zshrc` | no | yes | 71 / 101 ms |
| Fixture: `.zprofile` setup, `.zshrc` prints a banner | yes | yes (46 bytes of banner ignored) | 94 / 99 ms |
| Fixture: `.zshrc` sleeps 6 s | yes | **timed out**, killed | 94 / 6,066 ms |

The adapter then ran with the found paths in 20 of 20 launches, median 177 ms.

The test Mac's system-wide login files already put the tools' folder on
every login shell's PATH, so the fixtures skip the system login files
(`unsetopt GLOBAL_RCS`) to stand for a Mac whose do not.

An interactive zsh ignores SIGTERM. The first version sent a polite
terminate on timeout and the slow shell answered late anyway; a timed-out
probe must be killed (the app: in its own process group, killed as a group)
and its late answer dropped.

**Consequence for §6.7.** Discovery probes `-l`, then `-l -i` with a 5 s
limit and a kill, reads only between markers, and falls back to
"Choose location…". The paths are confirmed by the user and stored, so the
probe runs once, at onboarding, not per call.

## 4. Would bundling upstream be better than calling the installed one?

Asked because finding `node` and `claude-multiprofile` might prove
unreliable. It did not on this Mac (20/20), and the fixtures show where it
fails elsewhere (no path at all; setup only in `.zshrc`). What bundling would
cost, measured:

| | Measured |
|---|---|
| Node itself | Node 26 as Homebrew builds it is a 133 KB launcher over `libnode` (61 MB) plus about 110 MB of shared libraries (ICU alone 77 MB). The official single-file build is smaller but was not downloaded to measure |
| Upstream | 2.6 MB with its dependency, 312 KB of source |
| Signing | That build is ad-hoc signed. Shipping it means signing a JIT runtime under Sidelauder's Developer ID, with the hardened-runtime exceptions V8 needs, against §7.4's "no entitlements beyond the defaults" |
| Two copies of upstream | The launchers run the helper that the **installed** version wrote (`launch.js`, helper version 1), and the installed version decides the registry format, the copy paths and the process matching. A bundled copy at another version would classify by different rules than the launchers act by |
| Security updates | Sidelauder would ship Node's CVE fixes, and upstream's |

**Recommendation: do not bundle.** It would re-implement the foundation by
copying it, which is what §7.0 excludes, and the reliability it would buy is
available cheaply: the second probe, the manual location, and an "upstream
unavailable" state that names what is missing. The fallback belongs beside
D-20: if discovery fails for a real share of beta users, ask upstream for a
fixed install location (for example a Homebrew formula that puts
`claude-multiprofile` in a known prefix) before considering a bundled copy.

## 5. Findings for upstream and the spec

- **`doctor` makes a network call** (`npm view claude-multiprofile version`)
  even without `--fix`. Spec 4.1.22 says only `upgrade` does; it is corrected
  in v0.3. Sidelauder never runs `doctor` (it copies the command for the
  user), so I9 holds.
- **`runningCopies` matches by substring** (§1 above). Worth fixing in U1's
  classification: match the executable path at the start of the command, as
  the helper's own `running` does.
- **No exported classification.** The helper and `doctor` each draw the
  on-profile and stray lines inline; U1 would give them one home.
- **`refreshing` is not exported.** The helper writes `<copy>.refreshing`
  while it rebuilds a copy, but no function reports it; the adapter leaves
  `app.refreshing` out rather than hard-coding the path.

## 6. Not covered

- macOS 26 (moved to M2 with the other spikes).
- A true cold call, and a Mac with a Node version manager (nvm, fnm, volta)
  rather than the fixtures standing for one.
- A real Dock click on the Discovery app: the runs used a LaunchServices
  request from a process holding only the Dock's environment, and checked the
  app's PATH, but no one clicked a Dock tile.
